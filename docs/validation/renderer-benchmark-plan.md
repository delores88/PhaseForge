After the ongoing user research is complete or deliberately paused by the coordinator, run three paired repetitions for each of two load conditions: no study solver active, and one real CPU argon solver active with CPU platform, one thread, 32 particles, 120 K, 0.8 g/cm³, friction 1/ps, seed 314159, 1 fs step, sample interval 20. Reuse the exact load request for each repetition and allow no Blender/ML/GPU render workload to overlap. Record any unrelated machine activity; repeat the *pair*, not only the unfavorable member, if a prespecified interruption invalidates it.

Pair order is baseline/candidate, candidate/baseline, baseline/candidate. Each member has 5 seconds warm-up and 30 seconds measurement. Dispose its renderer and verify the canvas/context was released before opening the other member. Use one renderer at a time. A deterministic public-camera orbit of ±3° about the frozen direction provides equivalent active interaction; external seek selects the same ordered retained frame index from elapsed time. Do not use different native 15-second versus 30-second defaults. Record requested and actually displayed frame IDs and asynchronous lag. Static captures use the frozen nominal camera, not the moving camera.

Collect all raw timestamps, not only a final FPS number. Passive timing around the existing renderer submission can measure CPU submission time and actual render-call intervals without changing rendering features. Report per-repetition median/p95/p99 intervals, fraction over 33.3 ms, render calls/triangles, actual drawing-buffer dimensions over time, cache bytes, startup-to-first-decoded-state time, requested/displayed frame lag, and any WebGL errors or context losses. `renderer.render()` duration is CPU submission time, not GPU completion time. GPU timer-query measurements, if available and non-disjoint, must be separately labeled and consistently enabled for both.

Sample RAM and VRAM at 1 Hz during the same intervals. Record process IDs and the exact measurement method. Private bytes and working set are different metrics. If the harness shares a browser renderer or GPU process with other tabs, aggregate process memory is confounded and cannot be reported as per-viewer allocation. WDDM/driver VRAM readings may be unavailable; label them unavailable, never zero. Do not claim a memory win unless process ownership and comparable isolation are established. The actual installed candidate's process tree should also be sampled during its native acceptance run.

Save PNGs and raw metric JSON for every repetition, including failures. Independently check that visible body centers project from the exact retained coordinates, the same 108 IDs are supplied to both viewers, and the camera/drawing-buffer invariants hold. Inspect sphere silhouettes, surface faceting, clipping and distracting artifacts at the same scale. A rendering-quality improvement may cost more GPU work; report that tradeoff. A claim of smoother playback requires lower measured frame-time variation, not simply more polygons or a selected flattering still. No absolute speedup or memory reduction is predicted by this plan.
