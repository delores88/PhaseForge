# Bundled scientific runtime v2

The application now selects an offline, shipped runtime rather than discovering a host Python installation or installing packages from PyPI. This is dependency provenance; trusted shipped solvers still run under process supervision. Agent-generated code separately requires the Windows LPAC boundary.

## Frozen source contract

- `tools/runtime-seeds/science-v2.manifest.json`: SHA-256 `fcc53f3bc276e6c0101bdcc1f2d256b9f89942c9a6426b241d2a0aa4bb478aba`; CPython 3.13.15, NumPy 2.4.6, OpenMM 8.5.2, Pillow 12.3.0. The outer inventory covers 2,157 files / 169,645,038 content bytes.
- `tools/runtime-seeds/python-numpy-v2.manifest.json`: SHA-256 `bb2bbd5163b1cc488fa32e7b663974b3bb23b3edf6dc579af6e9fd7c138d3a52`; CPython 3.13.15 and NumPy 2.4.6. The outer inventory covers 1,509 files / 68,603,523 content bytes, including the separately pinned inner isolation manifest.
- `scripts/release/build_seeds.py` records the embedded interpreter, CPython source archive and pinned wheels, transformations and licenses. The source standard library is retained. Runtime launch uses `-I -B`, with optimization disabled; no `-OO` or bytecode-only standard-library substitute.

Production looks only under the executable's sibling `runtime-seeds/<kind>` resources when creating a managed runtime. Debug builds may explicitly set an absolute `PHASEFORGE_RUNTIME_SEED_ROOT`; release builds ignore that override. The managed destinations are `data/environments/science-v2` and `data/environments/python-numpy-v2/runtime`, with `python.exe` at each runtime root. Existing v1 directories remain untouched. A missing, changed or incomplete v2 runtime fails closed, with no host Python or network fallback and no in-place repair.

## Verification and publication

`backend/src/laboratory/runtime.rs` compares the outer manifest bytes to the manifest embedded at compilation, validates upstream source pins, and verifies the exact file set, byte lengths, hashes and native inventory. Paths cannot traverse, use alternate data streams or Windows aliases; extra directories/files, links, reparse points and hard-linked files are refused. A generated runtime's inner manifest must agree with its compiled outer pin and all file/source entries. The public LPAC launch path requires that v2 outer; it cannot fall through to a self-described legacy inventory.

A new copy uses a unique sibling staging directory, verifies every copied byte, verifies both staged and original inventories again, then publishes through a directory rename. Cancellation leaves an unselected staging directory for diagnosis. Copying requires declared content bytes plus a 64 MiB free-space reserve. This is a checked reserve, not a filesystem quota. Existing destinations are verified and reused unchanged; corrupt destinations are retained and refused.

The trusted readiness check reports Python/package versions, `sys.path` and module origins, and integrates a nonzero harmonic force in OpenMM Reference. The acceptance code also exercises the production OpenMM CPU, diffusion and mechanics startup paths with actual retained numerical states and preseeded worker/dependency provenance. LPAC acceptance runs real NumPy linear algebra and reopens a retained NPZ with `allow_pickle=False`; synthetic outside read/write/hardlink, runtime write and loopback/external connection probes must fail.

## Evidence status

The deterministic inventory/source/path tests initially passed 2/2. Actual copy attempt 1 retained real OpenMM and LPAC numerical/negative-probe receipts in `.local/validation/runtime-v2-20260911-attempt1`. Its final module-origin assertion failed because `sys.executable` used a native extended Windows prefix while module paths used the equivalent ordinary drive form. The failure is retained as `failure.json` and `lpac-work/stderr.log`. The checker now strips only that local extended-path prefix before containment comparison; package bytes, sandbox permissions and scientific criteria did not change.

Actual rerun passed in 44.53 seconds: `.local/validation/runtime-v2-20260911-attempt2/report.json`. Both copied inventories remained unchanged after real execution. The OpenMM Reference system moved under nonzero force; NumPy retained/reopened its solution with maximum linear residual `4.440892098500626e-16`. LPAC token checks reported AppContainer=1 and LessPrivilegedAppContainer=1. All six negative probes were denied; no provider environment keys were inherited. Module origins and `sys.path` were confined to the copied runtime and its source `Lib` directory. Mutating the outer manifest then attempting launch was refused; restoring the exact original bytes was a fixture-only cleanup. An absent seed created no selected destination. The preserved v1 marker remained byte-identical.

The three actual solver service entries passed in 20.13 seconds, with `service-entry-report.json` in the same evidence directory: OpenMM CPU, diffusion, and mechanics each completed with retained states, a real readiness check, manifest and preseeded requirements. The final runtime inventory verification passed after all three jobs. These are bounded startup/integration checks, not replacements for the separately frozen scientific accuracy studies.

The existing generated-service lifecycle acceptance then passed in 38.45 seconds using new offline v2 provisioning. `generated-service-report.json` and `service-79468145-4183-4524-81fe-2f2aadd1d92c/` retain the result and durable job data. It checked an actual saved NumPy solve, Timer Off remaining active until explicit pause, a new immutable restart with ancestry and deadline, storage-overrun termination with declared soft-limit semantics, and rejection of NaN result JSON after a successful process exit. None of these actual tests was skipped.

A read-only inventory review found no blocking schema/publication defect. Two additional guards were adopted: the opened Windows handle's final path must equal the expected local path, and the native inventory must cover every DLL, PYD and EXE. Device aliases and network/device roots are also refused. These guards preserve the compiled package bytes and do not broaden scientific claims. No installed-application acceptance is claimed by these component tests.

To reproduce with a fresh output directory on Windows, set `PHASEFORGE_RUNTIME_SEED_ROOT` to the absolute verified source seed root and `PHASEFORGE_RUNTIME_ACCEPTANCE_ROOT` to a new absolute evidence directory. Run `cargo test --manifest-path backend/Cargo.toml --lib copied_v2_runtimes_execute_source_stdlib_science_and_lpac_negative_checks -- --ignored --nocapture`, then `cargo test --manifest-path backend/Cargo.toml --lib copied_v2_runtime_runs_all_three_real_solver_service_entries -- --ignored --nocapture` against that same completed evidence root. For the generated lifecycle test, additionally set `PHASEFORGE_ISOLATION_TEST_ROOT` to the evidence root and run `cargo test --manifest-path backend/Cargo.toml --lib generated_actual_lpac_compute_restart_storage_and_deadline -- --nocapture`.
